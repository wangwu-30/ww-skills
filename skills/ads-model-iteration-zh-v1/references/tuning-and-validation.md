# 调参与验证

当问题涉及如何诊断回归、解释参数、选择下一项实验，或解读离线与线上证据时，读取本文件。

## 稳定的调参顺序

诊断或提出迭代方案时，优先按以下顺序：

1. 目标定义；
2. 样本构造；
3. 特征假设及训练、服务一致性；
4. 模型结构；
5. 服务、稳定性和实验风险。

这个顺序很重要，因为许多表面上的模型问题实际是：

- 样本时机问题；
- 特征不匹配；
- 预算桶伪影；
- 相邻阶段产生的链路反馈。

## 如何解释参数

用户提供 JSON 片段或实验配置时，按以下顺序分析：

1. 识别它影响的阶段；
2. 识别它要改变的目标；
3. 按作用对参数分类；
4. 解释预期影响方向；
5. 说明主要风险；
6. 建议最小验证计划。

### 有用的参数类别

- `switch`：是否启用某条路径或逻辑分支；
- `weight / beta`：信号或子分数的贡献强度；
- `threshold`：门控条件或分段边界；
- `tag / routing`：哪一部分流量会使用该逻辑。

### 实践规则

仅凭配置片段，不要假装知道精确线上影响。没有代码或实验依据时，应解释可能的方向和风险。

## 按问题类型给出的调参线索

### 延迟反馈症状

常见表现：

- 转化相关指标不稳定；
- 线上线下结果不一致；
- 长周期标签噪声较大。

优先采取的行动：

1. 检查标签时机假设；
2. 检查 `fast emit` 和负样本延迟行为；
3. 考虑多窗口或辅助任务设计；
4. 重新检查线上与离线的比较方式。

### 冷启动症状

常见表现：

- 新广告效果差；
- 历史稀疏实体的结果方差高；
- 过度依赖 ID 特征。

优先采取的行动：

1. 增加泛化特征；
2. 降低对 ID 特征的刚性依赖；
3. 尝试 `Feature Mask` 或 `Meta Learning`；
4. 如果可用，加入考虑不确定性的探索。

### 校准或偏差症状

常见表现：

- 高估或低估；
- 成本达成较差；
- 排序尚可，但价值质量较差。

优先采取的行动：

1. 分开诊断排序与校准；
2. 检查偏差是否只出现在特定分群；
3. 尝试校准或考虑校准的多任务设计；
4. 在认定只是校准失败前，再检查延迟反馈。

### 稳定性症状

常见表现：

- 消耗下降；
- 指标尖峰；
- 日间表现不稳定；
- 线上收益无法复现。

优先采取的行动：

1. 检查样本节奏和数据流；
2. 检查训练与服务的特征一致性；
3. 检查 `AA` 与预算桶效应；
4. 最后再评估是否需要改架构。

### 链路一致性症状

常见表现：

- 召回、粗排和精排彼此冲突；
- 上游模型学到了下游伪影；
- 接入服务后收益消失。

优先采取的行动：

1. 清楚说明完整链路；
2. 确定哪个阶段实际拥有该目标；
3. 决定与下游排序对齐，还是保留阶段专属目标；
4. 留意正反馈环。

## 离线评估注意事项

默认不要把离线收益作为充分证据。还要考虑：

- 延迟反馈造成的失真；
- `AA` 不一致；
- 预算桶效应；
- 阶段间的链路反馈；
- 服务约束。

如果方案只提升离线 AUC，应明确指出单凭这一点证据不足。

## 实验解读

解读实验时常见错误：

- 只相信一个 uplift 数值，不检查实验机制；
- 忽略预算拆分造成的失真；
- 忽略实验组之间广告分布的变化。

除 uplift 外还应检查：

- 实验机制是否带来流量或预算偏差；
- 收益是否持续；
- 线上路径是否符合预期的服务链路。

## 建议的输出模板

回答调参或参数问题时，优先按以下结构组织：

1. 阶段
2. 目标
3. 参数或瓶颈
4. 建议的调参方向
5. 预期效果
6. 主要风险
7. 验证方法

除非用户明确要求详细说明，否则保持简洁。

## 不应采取的做法

- 未检查样本和特征前，不建议先改架构；
- 不把离线 AUC 提升当作充分证据；
- 未说明时，不要把多个阶段混在一个回答中；
- 不假设所有排序问题都是校准问题，反之亦然。
