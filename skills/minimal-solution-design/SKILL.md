# 最小合理方案设计

选择满足当前、有证据支持的义务的最简单设计。不要把某个项目的实体、事故或偏好当成通用规则。

调查和评审不授予开发、生产操作或发布权限。已授权的工作继续推进，不重复申请已有授权。

## 1. 先诊断

读取适用的项目规则、权威架构、相关决策和历史。按“触发 → 预期行为 → 实际动作 → 被破坏的预期及后果”定义问题，写明必守条件、禁止状态和本次不做的事。

追踪实际入口、写方、读方和外部副作用，区分仍在运行与已退出的路径。分清观察事实、推测原因和证据缺口。先判断属于输入/环境故障、局部实现错误，还是反复的机制失效，再选修正范围。同类故障反复出现时查共享假设；重复本身不证明要换架构。

会改变诊断或方案的缺失事实，由作者在授权范围内查源码、日志、产物、历史和只读工具，沿有用的引用继续查，不止于用户给的附件。评审指出的证据缺口也由作者补。只有以下情况才结束一个调查分支：该事实已不影响行动；数据来源不可用、访问失败或操作被禁止；剩下的是只有用户能给的私有上下文或业务决定。这时记下已查内容和具体阻断。

## 2. 查明真实义务和历史意图

代码、默认值、结构定义和测试只证明现状，不证明必要性。读架构决策（ADR）的理由和前提，不只看“已接受”标签；没有记录也不等于没有真实使用方。判断“兼容无关”之前，先查活跃调用方、持久数据、在途工作、需要重放的历史和已发布合同。

旧决策只在前提实质变化，或有依据表明显著净收益时重新评估，并写清“原意图 → 变化事实 → 新意图 → 仍须履行的义务”。过时的理由不取消已发布的承诺。确实缺少业务选择时，先取得该选择，再做依赖它的工作。

## 3. 选出最小方案

从现有权威路径开始，只增加当前义务确实需要的内容。对拟新增的抽象、表、状态、节点、适配器、后台进程、版本分支和复制数据逐项问：它解决哪个已验证的问题？谁是真实的生产者、归属方和使用方？它删除了哪些既有复杂性？删除、内联、收窄或复用既有扩展点，能否满足同一义务？

准备自建缓存、隔离、恢复、调度或验证机制前，先查现有技术栈的原生能力、仓库已有工具和成熟库的官方方案，确认它们能否保住本次真实使用方的事务、并发、身份和清理语义。能用就用；自建只补已查明的缺口，并说明成熟方案为何不适用。也不为了“用了现成的”引入不必要的依赖或运行框架。

比较候选时：

- 必守条件是有效性门。违反任一条的候选直接淘汰，不参与排名。
- 候选里必须有删除、收窄或复用既有能力的方案。先给每个候选最强的支持理由，再攻击它的关键假设、总代价和具体失败场景；不拿弱备选衬托偏好的方案。
- 会改变排名的争议，读直接证据或做范围内的有限验证。不虚构工期、收益或概率。
- 假设推荐方案最依赖、风险最高的那个假设是错的，它还成立吗？不成立就补查或换方案。
- 总代价计入开发、验证、协调、运行、维护、迁移和用户工作，不只算新增代码量。打平时选更小、更可逆、维护成本更低的方案；不可逆的动作需要更高的证据和明确的损失说明。

最后给出一个推荐。常规技术取舍由 Agent 决定，不罗列方案让用户选。用户另行点名 `force-thinker` 时，用它完成本节的比较，其余步骤不变。

涉及等待/重试/交接、外部副作用、兼容或迁移、归属和依赖方向、新增检查或门禁时，提案前读取[工程细则](references/engineering-checks.md)的相关章节，不加载无关章节。

## 4. 挑刺和消融

在必守条件不变的前提下，逐项拿掉或简化方案里的关键机制，检查同一组正常、失败和并发场景。更简单的方案仍满足要求就采用；必须保留的机制，要说清拿掉后具体怎样失败。区分推演和实际实验；会改变状态的实验在隔离环境执行。

改变职责、持久状态、外部副作用或兼容范围的设计，允许委派时请一位非作者的挑战者评审：给原始问题、约束、历史、当前候选和一手证据，不暗示结论。意见必须指出具体违反的要求或无依据的主张；作者逐项查证后修改或反驳，根因被推翻时回到诊断。实质简化后，只把新候选交回同一挑战者复核受影响的部分，不设固定轮数。无法独立评审时说明这一限制。

重要设计在项目里保持一份决策记录：问题与证据、候选、被否定的路径及理由、挑刺和消融结果、未决事项和状态（`proposed / accepted / superseded`）。行为已确定的简单修改不需要。

## 5. 实施和验证

已授权就实施收敛后的方案；只要求评审时交付具体建议。新业务含义、外部承诺、不可逆处理或范围扩张确实需要决定时，先完成可审阅的提案，等待期间继续独立工作。

在合适的边界和版本上验证改变后的行为，复用有意义的既有检查。不写只复刻实现或匹配措辞的测试。结构合规、实际行为、部署和真实验收分开记录；新证据推翻前提时回到诊断。审计或测试本技能时读取[行为案例](references/behavior-cases.md)。

## 6. 交付

最终答复按[沟通 Skill](../decision-partner-communication/SKILL.md) 写，包括其中的准确压缩。本技能只规定答复必须覆盖的内容：

1. 推荐方案，以及有意删除或避免的机制；
2. 必守条件、禁止状态和不做的事；
3. 归属、依赖方向和兼容方式（相关时）；
4. 推荐处于哪一步：原因仍未查明、原因已明但方案待定，或已收敛。调查计划不是已选定的修复，建议不是已实现的结果；
5. 确实需要用户决定的事项。

一个方案明显更优时不罗列变体。已授权且方案已定时直接实施，不做形式化的架构表演。
