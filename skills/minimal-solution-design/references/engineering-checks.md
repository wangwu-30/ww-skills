# 按问题读取的工程细则

问题或备选方案涉及下列职责时，读取相关章节。细则补充主流程，不增加执行权限或第二套评审循环。

## 等待、重试和交接

提出涉及持久等待、重试、交接或外部副作用的方案前，走通一条正常路径及一条相关失败／并发路径，包括等待期间到达的输入或事件。每次转换都要确认：谁负责未完成工作和已接受输入，谁仍能产生副作用，什么证据和授权允许下一步。

使用方等待时，来源游标前移、确认收到或替换最新快照，都不证明已经处理完成。仍有意义的工作必须保持可发现，明确顺序和责任，直到被处理或明确被替代。路径应走到合法的后续动作或明确终点；缺失出口标为未解决。沿主流程的真实义务与历史意图复核旧机制，不默认保留。

## 找到最小合理实现

以现有权威路径为基线。先查删除或替换不必要机制能否避免扩展，再只增加当前义务需要的内容。

对拟新增的抽象、表、状态、节点、适配器、后台进程、版本分支和复制数据逐项问：

- 它解决了哪个已验证问题？
- 谁是真实生产者、所有者和使用方？
- 它是否有独立生命周期或含义？
- 它删除了哪些已有复杂性？
- 能否通过删除、内联、收窄或复用已有扩展点满足同一义务？

新概念需有具体依据，例如独立生命周期、真实公开合同、多个真实使用方共用的条件，或需要持久幂等与回应丢失恢复的外部副作用。这些依据不自动授权新增一层。

优先选择以后容易扩展的方案，不预建灵活性。新增项带来的协调、同步或迁移工作若超过它所解决的义务，就拒绝它。

## 明确决定兼容范围

不预设全面兼容，也不预设彻底切换。先盘点真实义务：

- 活跃调用方和可选择入口；
- 持久数据和在途工作；
- 仍需执行或重放的流程／事件历史；
- 外部客户端和已发布合同；
- 运行保留期限与升级承诺。

只选择实际需要的方式：

- **彻底切换**：撤下旧选择与写入路径，不保留活跃回退。
- **冻结旧版**：停止新增使用，只保留已有对象需要的读取器或执行器。
- **迁移**：明确来源、目标、原子性、回滚和完成证据。
- **限定兼容**：明确支持对象、责任者、退出条件和删除时点。

若选择会改变产品行为、历史承诺或运行责任，且现有证据不能决定，交给业务负责人作必要选择。不要默默实现所有方式来防备假设需求。

## 保持单向所有权和依赖

- 每个持久事实只有一个所有者和一个权威写入口。
- 模块依赖它直接使用的窄而稳定的合同，不依赖遥远的上游内部实现。
- 版本或提供方格式在边界只转换一次，不将差异传遍所有下游模块。
- 只传下一步需要的信息。使用方能安全读取权威对象时，优先传稳定引用，不复制整个对象。
- 视图、缓存、摘要、检查点和传输数据默认是派生信息；有独立生命周期和明确权威时例外。
- 避免循环导入、反向查询、双向同步和跨多个存储的相等检查。出现这些问题时，先复核归属，再加对账。

例外必须说明：保护什么条件、为何单向边界不能保护，以及谁负责最终一致。

## 用结构限制错误设计

优先采用能约束实际行为的结构：

- 函数和命令只接受必要输入；
- 类型排除无关上游字段；
- 数据库外键、唯一性和事务写边界；
- 每种状态转换使用唯一应用命令；
- 依赖规则阻断禁止的导入或调用；
- 明确失败，不走无人负责的回退。

测试和发布检查应验证这些结构是否保护了要求，不能代替结构本身。

## 新增检查前先确定责任

建议检查、门禁、探测或复制事实前，确认谁负责、事实何时变化、哪个阶段使用、什么失败必须停止。选择最早能取得必要事实的阶段，不在更早阶段猜测：

- 文档解释意图和合同，不执行业务策略。明确版本化的配置和提示可能是真实运行输入，应按使用方判断，不按文件后缀判断。
- 实现负责业务判断和变化输入。测试验证已确认行为；测试报告或评审方便都不支持额外业务状态或第二套实现。
- 构建、部署或进程启动负责固定装配、安装工具、版本和静态能力发现。没有具体失效原因时，不在每次业务调用中重复这些证明。
- 运行阶段检查当前请求、新生成产物、取消、期限、租约和未知外部副作用。启动成功不证明之后这些事实。

重复静态检查时，先复用已准备的值，或合并已有读取批次；不要只为去重引入通用缓存、就绪框架或新权威。启动已验证，仍须处理实际运行中的输入输出失败。不要每次操作都重新发现能力，也不要借精简删除动态验证。

边界发现按以下关系说明：

实际调用点和频率 → 变化或固定的事实 → 应负责的阶段与最小修正 → 受影响行为及证据。

源码里的超时上限不是实测延迟。评审只授权发现和建议，不授权生产修改、测试扩张或部署；改变业务语义或超出请求范围时，先取得必要决定。
