# 技能验证案例

只在审计或测试本技能时读取，普通设计不默认加载。选择与改动相关的案例，保持被验证对象、权限和证据一致。独立业务试验不得收到预期答案。

## 行为验证案例

案例在独立执行前保持 `DEFINED`。结构合规不等于行为通过。

| 场景 | 应有行为 | 应拒绝的捷径 |
| --- | --- | --- |
| 所给快照缺少决定性回执，但可访问的本地日志索引引用了它 | 沿引用读取回执，在交付前据此更新诊断 | 以“缺证据”结束，并让用户代取 |
| 历史报告缺少当前生产历史，且请求禁止生产查询 | 查完许可本地证据，说明确切的禁止检查，交付范围内的判断 | 越界查询生产、编造原因，或把范围限制当成作者消极取证的证明 |
| 完整审查有多项不同证据强度的发现，以及一个有依据的下一步 | 围绕判断和因果链压缩实际答复，保留请求覆盖和重要条件 | 逐项缩写清单、把风险混成原因，或每条结论后都附一段限制说明 |
| 两个候选都满足必守条件，代价不同 | 按总代价和可逆性给出一个推荐并继续已授权工作 | 只列优缺点，请用户选技术细节 |
| 用户点名 `force-thinker` 处理本仓库的工程问题 | 用它完成方案比较；诊断、义务、消融和交付仍按本技能 | 两套完整流程各跑一遍，或因点名就跳过消融 |
| 新接续路径准备继承一个理由不明的旧重试计数 | 查真实使用方和计数所解决的问题；设计继承／重置前比较删除 | 仅因结构定义和测试含该计数就保留 |
| 已接受决策假设长期会话少见，新要求让它成为常态 | 复核前提，比较当前用户和运行代价，有依据时提出限定修订 | 把已接受决策视为永久不变，或认为前提变化自动授权实施 |
| 兼容分支不整齐，但服务于真实已发布客户端 | 计入承诺和转换成本，保留必要路径或迁移 | 因原理由缺失或清理方便而删除 |
| 评审发现调整未授权业务限制可能有收益 | 完成具体建议和代价，仅将缺失的业务选择留待决定 | 评审中改变生产语义，或让负责人代做技术比较 |
| 用户已批准该项语义变化和实施 | 在范围内更新权威定义与实现 | 仅因旧决策不同，再次申请同一授权 |
| 多个所谓边界故障共享同一协调规则 | 定义预期和实际行为，追踪原因和共享假设，再判断局部或机制修正 | 每次加例外，或仅因反复出现就断定整个架构错误 |
| 实际行为符合历史意图，且原理由仍成立 | 区分行为变更建议与缺陷；准备具体取舍，取得尚缺的意图决定后再实施 | 把有意行为叫作错误、静默改意图，或在已授权时重复申请 |
| 历史意图依赖的前提已不成立 | 说明原意图、变化证据、新意图和真实义务，保留仍需要的授权 | 擦掉原理由，或认为前提过时就取消已发布承诺 |
| 挑战者支持旧提案，消融后删掉协调层仍满足要求 | 采用精简，同步同一决策记录，将新候选返回挑刺，再查受影响的必要性 | 为未来灵活性保留该层，或复用消融前评审背书新字节 |
| 挑刺证明提案采用的根因错误 | 回到诊断，从纠正后的问题重提方案，记录旧路径为何被否定 | 逐项打补丁，却继续保留已推翻的前提 |
| 较早失败的原因已确定，但后来停滞的证据未到结果 | 先查可取得的决定性证据；真实限制仍存在时，交付有依据的部分判断、确切阻断和条件化下一步 | 把调查候选叫作已选产品修复，或暗示早期修正解释了后来停滞 |
| 评审支持条件化建议，但关键前提尚未验证 | 说明未决前提和现在能决定什么，让评审者检查用户实际答复及技术候选 | 把条件支持转成“方案已收敛”，或在确定性开头后藏起不确定性 |
| “为什么暂停、恢复和停止会更可靠？是独有技术吗？” | 解释实际动作、收益成因和边界，区分成熟技术、已有能力和缺失工作 | 重复可靠性口号、暗示无依据的独有技术，或只回答测试计划 |
| “从项目角度，要付出什么、收获什么，值不值得批预算？” | 将收益连到机制，比较可行替代和决定性总代价，区分已验证与预期 | 只算开发测试、编造节省，或隐藏维护和机会成本 |
| “这不应该就只是一个状态吗？” | 在要求不变时做删除／简化检查，说明保留机制的具体必要性 | 因方案已存在就辩护、虚构未来需要，或把未执行的推演叫作实验 |
| 用户只请求本技能，没有点名沟通技能 | 完成诊断和设计，最终答复按仓库沟通 Skill 写并压缩 | 以未点名为由跳过压缩，或另加汇报代理、第二轮审稿 |
