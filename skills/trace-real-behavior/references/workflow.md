# 从仓库调查到修复 PR

适用于“分析这个仓库并找问题”“找一个已有 PR 尚未覆盖的 bug”“复现这个问题并修复提交”等任务。先按用户目标选择下面的工作范围，再应用 [Skill 正文](../SKILL.md) 中的因果追踪与验证方法。本文不是每次都必须走完的审批流程。

## 选择范围

| 用户要的结果 | 工作范围 | 完成条件 |
|---|---|---|
| 理解仓库或核对一个行为 | 建立必要背景，沿真实入口解释 | 当前源码与证据足以回答；不自动改业务代码 |
| 扫描问题 | 调查候选、排除误报、复现偏差 | 交付符合用户范围的问题及证据；找不到时说明已查范围 |
| 找到已有 PR 未覆盖的问题 | 在扫描中增加已有工作去重 | 复现成立，并能说明相关 PR 与当前主分支的覆盖情况 |
| 修复并提交 PR | 在已确认问题上实施、复验、评审、发布 | 已创建正确目标和提交的 PR，并回读核实；不等于已合并或发布 |

用户已经授权实施或提交时，继续完成对应工作，无需把阶段切换变成重复确认。调查请求本身不授予推送、发布或合并权限；只把无法自行查明且会改变动作的信息交给用户决定。

## 1. 从实际入口建立背景

核对仓库、版本、分支、工作区改动和项目约定。已有地图或先前结论可以缩短寻找入口的时间；涉及当前行为时仍回到源码核对。如果仓库陌生，可使用仓库分析工具或已有的 repo-alive；不要求先完成整库分析才能修一个局部问题。

围绕调用方的任务选择一条链路，说明谁提供什么输入、谁加工、最终谁消费。沿这条链寻找合同与实现的差异，并把疑点写成可证伪的问题。函数很长、模块很多或实现看着别扭，只能作为调查线索。

并行调查确实能减少等待时，可以把互不依赖的入口交给不同执行者。每份结果应包含版本、真实调用链、预期来源、执行证据和未查范围。主执行者合并证据并处理重复候选；几个执行者得出相同猜测不等于完成复现。

## 2. 按目标查已有工作

仅当用户要求新发现、避免重复提交或判断已有修复覆盖时，读取并应用 [001 去重补丁](patches/001-novelty-pr-dedup.md)。尽早取得包含 open、closed、merged 的相关 PR；不要花完调查成本才检查问题是否已有修复。

先用清单、文件和关键词缩小范围，再查看相关实际差异。比较的是根因、真实路径和修复覆盖，不是标题是否一样。对每个成熟候选保留以下一种判断，并给出依据：

- 同一根因已覆盖：排除重复交付；若用户要复现或验证该 PR，则继续其指定任务。
- 相关但未覆盖：说明仍存在的入口、条件或边界，以及已有修改为什么没有处理。
- 暂未找到覆盖：记录查询时间、状态、分页和版本范围，不把有限搜索写成全局首次发现。

如果本地版本落后，核对当前主分支的相关实现。需要宣称“当前全部已有 PR 未覆盖”时，应能够交代完整清单及文件/差异核对的范围；无法取得的部分保持未知。普通指定修复不新增全量 PR 扫描要求。

## 3. 把候选推进到真实反例

追到消费者之前，候选只能称为怀疑。找到合法上游输入和独立预期后，运行最小真实入口或子链，记录原始输入、必要中间值和结果。对配置问题尤其要追清读取时刻与优先级；对边界问题要把切片、过滤、归一化等前置转换连起来测试。

选择能够区分“修复正确”和“只让原例通过”的对照，并实际执行。可以根据合同采用边界枚举、性质检查或可达事件序列，但不通过构造不可能的内部状态证明生产故障。也要保留正常行为与推翻原猜测的证据。

遇到缺依赖或缺设备，先判断失败发生在哪一步。继续能执行的真实 CPU 子链或静态核对，同时保留未验证的设备、分布式和性能范围。环境启动失败不算产品 bug，局部验证通过也不算整条推理链通过。

成熟候选只需要足以复查的一份记录，通常包含：

- 调用方目标、预期来源和仓库版本。
- 合法触发条件、真实调用链、实际结果与影响范围。
- 最小复现、必要对照，以及环境或材料限制。
- 适用时的已有 PR 去重依据。
- 当前状态：待查、可达、已复现或修复已验证。

复用已有测试和命令输出，避免为同一事实生成多层报告。怀疑被推翻时记录原因并转向下一个候选；不要为了完成“找 bug”的任务而重新定义合同。

## 4. 修复并验证

在隔离分支或工作区内实施同一根因所需的修改，保留用户原有改动。先确认未改基线确实暴露问题，再用相同入口验证候选；涉及多个直接消费者时一起迁移。修复范围由因果关系决定，不由文件数决定。

使用项目已有的测试层级和材料。回归测试应捕捉真实可达的偏差，并覆盖本次修改可能破坏的语义类别。不要把实现复制进预期，也不要为一个局部问题搭建新的测试框架。

运行受影响的测试和项目要求的检查。检查通过后，仅在新修改、新失败或未解决的疑点出现时扩大或重复测试。性能改动另需可比较的基线、正确性对照和消费者关心的测量口径；减少调用次数不能替代真实收益。

对跨层边界或其他容易误判的修改，安排独立审查。审查者从当前源码、合同、复现和差异重新判断根因、下游影响与测试有效性，指出实际问题；不以“同意作者”作为通过条件。确认的审查问题修正后，重跑受影响的检查。

## 5. 提交并回读 PR

发布前核对最终差异、提交身份、目标仓库、base 和 head。PR 正文面向没有参加调查的维护者：说明相关功能与调用方，再给出具体触发条件、原行为、修复后的行为和验证范围。只包含最终实现需要的背景；不把探索日志或候选淘汰史全部搬进去。

用户授权提交 PR 后，提交并推送实际验证的版本，按项目约定创建 PR。沿用可用的连接器或 CLI；某个工具明确缺少权限时可以使用同一授权范围内的可用路径。不能通过换工具规避一项操作本身的授权限制。

远端写入返回不明时，先检查分支、提交或 PR 是否已创建，再决定是否重试。不要因响应丢失重复创建。发布后回读 PR，核对链接、目标、head SHA 和文件差异与本地交付一致。

最后交付 PR 链接、关键变化、实际检查结果和未验证范围。创建 PR、CI 通过、合并、部署及业务验收是不同事实，只报告已经观察到的状态。若任务只要求提交 PR，到此结束；只有用户另有授权才继续合并或发布。

## 6. 从实际失败改进方法

执行中发现 Skill 缺少关键指导时，先记录一个有证据的具体问题。使用单独、追加式的补丁，包含基线版本、真实观察、条件规则、适用范围和验证办法；之后的调整新增文件并说明替代关系，保留旧版本。不要把某个案例的要求变成所有任务的门槛。

将补丁统一合入正文属于新的方法版本，需要说明变化，不能沿用旧版本的验证结论。用户要求比较或优化方法时，再使用固定任务、冻结版本、新会话执行和独立评审；不要为每次普通 bug 修复自动启动大规模 Skill 评测。

评测要让执行者面对真实任务和最少原始材料，不预先泄露预期答案。保留失败、超时和缺失记录；同题重跑、同一夹具的多个排列不能当作多个独立问题。明确区分开发题、后补的回归探针与未参与调参的任务，并说明设计者是否看过题目。

必要证据齐备后交付结果；时间或预算不够时，清楚写出完成与未完成的部分。继续调查的条件应来自用户目标与尚待判定的问题，不来自“总还能再查一点”。
