# 从真实行为验证小范围问题

目标是完成调用方需要的判断或修复，并留下可复查证据。小 scope 指同一个问题的必要因果范围，不是固定文件数。简单 bug 仍值得查；也不要为了展示复杂分析而绕过简单解释。只有调查得到的真实依赖才能扩大读取和修改范围。

## 确认问题和合同

先核对仓库版本、工作区、实际入口和可用环境，复用仍适用的已有证据。选定一个调用者目标，如“这份评分是否把错误答案判对”“取消后这条请求会不会继续运行”。用户的怀疑是线索，不是事实。

从真实消费者、公开说明和现有行为测试独立确定预期。它们冲突时先说明合同疑问并追查，不自动把现状或注释当作正确答案。参数缺席与显式零值、未命中与成功、局部完成与全部完成可能含义不同。例如 abort 返回命中数 0 不能解释成取消成功；应先核其合同、请求当时在哪以及是否仍有后续动作。

写下可被反例推翻的判断：给定合法条件，实际输出应满足什么；什么观察会支持、否定或不足以判断。对 bug 不必设改进百分比。对性能若没有业务要求或波动依据，不凭空设收益阈值。

## 沿真实数据和时序缩小范围

先用 rg/符号/AST/import 或适合的数据流工具确定入口、生产者、转换与消费者，再只读有关实现；工具的结构结果和推断的语义分开。输入不仅是函数参数，也包括配置、共享状态、读取时刻、调用顺序和并发事件；输出也包括副作用、持有资源以及返回后尚未完成的工作。

针对疑问追查必要的几项，不把下面清单变成每次任务的全量门禁：
- 数量与单位：token/sequence、字节/元素、每请求/全批、平均的分母。
- 位置与边界：全局/局部索引、半开区间、padding、压缩或切片后的坐标。
- 集合操作：过滤、聚合、重复键覆盖、去重以及顺序是否影响消费者。
- 身份和共享：拷贝/借用/别名，配置在哪次 import、构造或调用读取。
- 生命周期：谁创建、使用、等待和释放；设备事件、异步结果、取消或重启后什么还会继续。
不能只看到单个函数自洽就断言组合链正确；也不能仅因跨了多个模块就断言设计有错。

对影响判定的每次转换，检查它是否保留下一步需要的上下文。比如先切片再做边界匹配，切片可能让一个本来位于词/数字内部的位置变成新字符串开头；局部匹配正确仍可能错误解释原输入。优先在真实组合入口验证这种前后边界，不只测试修过的叶子函数。发现它与当前偏差属于同一原因时纳入必要修复；无关的新问题保留线索，不顺带扩大本次任务。

## 使用合法输入建立反例

让上游当前合同允许的输入穿过真实消费者。例如模型可能输出错误答案或不遵守 boxed 格式，这仍是评分器应处理的合法 raw_text；但直接往内部对象塞入上游不可能产生的字段，不能证明线上 bug。

先跑足够小的真实入口或真实函数链，记录原始输入、关键中间值、结果和环境。预期须来自合同、独立计算或可靠参考，不能复制实现再用它判自己。按问题选方法：
- 有限边界或小输入空间：枚举和边界对照。
- 可描述稳定关系：性质测试，明确适用前提；重复写入采用“后值覆盖”时，不应要求冲突记录任意重排不变。
- 状态/取消/迟到结果：控制实际可达事件顺序，检验完成、失败和资源回收。
- 确定性小代码且输入、依赖可建模：可以符号执行；不先建通用分析平台，也不拿模型猜测当执行结果。

验证对照应从实际实现正在区分的语义类别导出，并实际运行；不能只把它们写进计划。例如提取文本中的数值时，既要覆盖触发问题的符号，也要检查合法普通格式、专用格式、精度/小数边界、位数限制和前置截断边界。具体类别取决于真实合同，不把这个例子变成所有任务的固定用例表。选出的每类至少有一个能区分“修复正确”和“只让原例通过”的输入，核对执行结果后再报告覆盖。

缩减后仍须保留入口可达性和关键合同。保留推翻怀疑的例子与“不改”结论。一个固定夹具的数百种排列只是一个探针的相关变体，不是数百个独立业务案例。

## 缺依赖时仍完成可做的判断

查实际解释器、扩展、依赖、设备及已有远端配置是否足以到达目标；未核实的远端不能算可用。区分环境未启动、合法输入没到消费者、程序行为不符。不要通过伪造设备、跳过关键实现或把异常改成成功来获得通过。

环境不足时继续做真实可执行的 CPU 子链、代码路径和独立参考检查，报告它们分别证明什么。设备内存安全、数值正确性、分布式退出和性能仍须相应环境验证；没有执行的路径明确写未验证。不要把一个局部探针扩成完整测试环境或整条链通过。

## 性能要测真实成本

先确定问题位于初始化还是热路径，以及消费者关心的总耗时、吞吐、延迟或内存口径。相同硬件/环境、配置、输入、负载和正确性条件下比较未改基线与候选；必要时成对重复，控制预热、编译、缓存、日志/profiler 和异步完成边界，报告差异与波动。

调用次数、文件行数、少一次扫描只提供待测假设。局部变快不证明总耗时或资源更好；也不能把业务输出减少、精度降低或遗漏异步工作当作收益。没有可比较环境或输入时给出最小测量方案，结论保持证据不足，不能声称提速。预算用完也不是通过。

## 修复、验证和交付

用户授权实施且已确认偏差时，在必要因果范围内修复，并迁移直接消费者；复用项目既有测试层级、夹具与运行入口，不为一个问题新建测试框架。普通测试使用受版本控制或可重建的合法材料；真实 checkpoint/设备专项明确注明依赖。覆盖与此修改相关的成功、失败、恢复/取消和清理路径，不机械枚举不存在的路径。

保留未改基线、首次失败、修改差异和复验。证据可以复用已有命令输出、测试文件和简短记录；不要为同一事实另造多份摘要或庞大的验证目录。先完成会改变结论的反例与必要复验，再整理交付；必要证据齐备后结束可选扩展，并及时给出结果。剩余预算不足时明确已经完成和尚未验证的部分，不让可选文档或重复检查挤掉最终交付。

说明影响范围前，沿各真实消费者核对中间结果是否被后续步骤覆盖、重新解释或只用于诊断。某分支观察到的错误不自动影响所有模式；读取过分支代码也不能代替向维护者说明适用范围。测试失败先确认到达目标以及环境/材料/替换点正确，再判断产品问题。保留真实的身份、格式、并发、事件与资源保护；不要把架构提案或未来功能需求混入修复。若现有行为符合合同，就解释并停止修改。

向不熟悉项目的维护者交付时，正文按读者建立理解的顺序写。开头先用两三句说明仓库和相关功能在做什么、谁把什么交给谁；不要先抛出误判标签、指标变化或修改结果，再要求读者到后文补背景。随后说明函数职责及真实调用方预期；再展示实际输入如何转换、偏差及影响，最后给修改和证据。不先堆符号或问题标签让读者自己拼流程。用自然叙述表达关系，文件/符号是可下钻的证据。

明确区分：怀疑（待查）、合法链路可达（已追到）、复现（实际运行观察偏差）、修复已验证（同类入口复验并覆盖必要反例）。说明没测的范围和会改变结论的下一条证据。不要只复述本方法，不宣称自己完全遵守便等于验收通过。
