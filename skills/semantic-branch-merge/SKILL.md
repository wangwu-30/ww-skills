# 分支意图与语义合并

先理解两边要改变什么，再判断变化能否共同成立。文字冲突只是编辑位置重叠；自动合并成功也不证明语义相容。

## 先区分评估与执行

用户只要求影响分析、成本预评估或方法讨论时，交付分析，不执行 merge/rebase、解冲、提交、推送或部署。需要试算文字合并时，先查工具是否会写 Git 对象或其他状态，不能把“不改工作树”说成“完全只读”。

已有实际合并授权时，在独立分支和工作树实施；保留原分支、未提交改动及约定的提交历史。合并授权不自动包含推送、MR 合入或部署。方法与证据成立条件未变时直接复用，不重新索取已给授权。

实际合并的交付目标是约定使用范围内可用的组合版本。最低要求是双方合并前有效的功能、修复、合同、安全保护及仍须支持的兼容行为继续成立；例外仅限明确适用的人类冲突裁定或既有退役决定。用户明确只要求解冲或候选时，才按该有限阶段交付。

## 1. 固定双方版本和分叉范围

记录仓库、两侧具体提交与全部最佳共同祖先，读取实际提交拓扑。区分原始历史分叉点、期间的同步合并与本次有效合并基线；不能把最近一次共同祖先当作全部开发历史的起点。

单一基线时分别读 `base..A`、`base..B` 的历史与净变化。出现多基线、重写历史或跨分支移植时，先解释有效分析范围，按需核对更早的原始意图区间和等价补丁；不任取一个祖先或重复计算已吸收的贡献。没有共同祖先时明确说明，不能虚构三路比较。

## 2. 分别还原两条意图与语义变化链

按需求和行为归组，不为每个提交另建记录。结合提交、MR、ADR、合同、实现与相关测试，回答：

- 原来有什么问题或约束；该分支想达成什么结果，适用场景和前提是什么；
- 相对基线，哪些行为、状态、身份、权限、接口、数据或外部副作用发生变化；
- 哪些实际生产者和消费者依赖它，哪些旧承诺仍须保留；
- 后续是否修正、撤回、替代或仅部分实现，最终分支实际保留了什么。

区分人明确要求的意图、Agent 从代码推断的意图、已实现行为和已验证结果。测试只证明覆盖范围内的行为；提交标题和设计稿不能单独证明实现。缺少可取证事实时自行补查，不把调查工作交给人。

用已有 MR/评估记录或紧凑表格承载即可，不另建固定格式账本或自动合规系统。

## 3. 比较语义关系，先核交互再判正交

以共同基线为参照比较 `原行为 → A` 与 `原行为 → B`。追踪共同消费者和共享合同，尤其是初始化、实际消费、错误处理、状态迁移、清理、迁移与回滚。不同文件也可能通过接口、配置、数据库或状态规则互相影响。

| 关系 | 处理 |
|---|---|
| 正交 | 有依据证明可独立成立、组合后不破坏双方义务；已获合并授权时直接整合，无须人逐项批准 |
| 同义重复 | 核对适用范围、可观察行为与旧承诺；确实等价且不涉及新取舍时收敛实现，保留贡献来源 |
| 存在交互但相容 | 明确组合后的调用顺序、合同和边界，再做工程整合；相互依赖不自动构成语义冲突 |
| 意图或语义冲突 | 同一场景下两边要求不能共同成立，或必须舍弃一方承诺；整理证据交给人裁定 |
| 关系未确定 | 标明缺口与结束条件，继续能改变分类的定向核实；不能把未知标成正交，也不能直接要求人猜 |

对自动合并成功的路径也检查交互。不能以文件数、冲突标记数、测试各自通过或“两个实现都留着”替代语义分析。AST/结构化合并可以辅助解冲，但不替人决定产品含义。

## 4. 把冲突的意图和语义交给人判断

给出共同基线、双方要求及依据、发生冲突的具体场景、不能同时满足的义务，以及可行取舍和各自后果。可提出推荐，但不能把推荐当成裁定，也不能暗中用“新版本优先”“更安全”或“保留双方”选择语义。

已有明确且仍适用的人类裁定时附上依据并落实，不重复讨论。一个 ADR 的 accepted 标签或提交时间更晚，本身不证明它已经裁定两条分支的冲突。

等待裁定时继续独立且已授权的工作；不要把一处未决语义扩大为所有工作的停工条件。实际整合不得让受影响的未决部分冒充已闭合。

## 5. 评估成本，或在授权后实施并验证

预评估按意图组、共享合同交互、待裁定项、迁移和实际验证要求拆解工作量。区分已有适用证据与还需取得的证据；提交数、变更行数和文字冲突数只作辅助信息，生成物与评测材料单独识别。

工程工时、机器运行/业务观察时间、人的裁定等待分开报告。只有事实和工作拆解足以支持时才给区间，写清假设及未确定部分；不能从冲突文件数直接推算工期。预评估结束于有依据的成本判断、可整合项和具体待裁定项，不把执行合并变成评估的完成条件。

实际合并获准且相关语义已确定后，逐处做工程解冲，不用整文件 ours/theirs 代替分析。分别以两侧准确父提交为行为基线，回查双方最终保留的有效成果，再验证共同消费者及组合后的新交互；确认旧修正没有复活，舍弃一方成果有明确适用的裁定。生成物与锁文件依据最终源重新生成，不拼接两侧摘要。

验证集中在双方改动相遇的真实消费者与边界，必要时覆盖失败、并发和副作用。合同迁移时保留原测试保护的含义，不能靠删断言、跳过失败或放宽合同放行。先完成组合定向验证；稳定并冻结候选后，沿仓库要求及实际影响范围完成最终检查。继承已有证据须说明成立条件没有改变，不能拼接两条旧分支的通过结果冒充组合通过。定向诊断须说明会影响行为的实际命令与环境差异，例如临时目录参数、执行身份、权限和数据库前置状态；单独重跑通过不证明已解释长序列中的原失败，归因须核对原错误栈及可复现的生产者到消费者路径。

先核对检查实际验证的对象。普通单测依赖受版本控制的测试数据和可重建环境，不要求任意执行机器共享未声明的历史安装目录。真实历史安装或现场材料检查放在明确提供输入的专项验收，保留其完整性与失败反例，单独记录 PASS 或未运行；缺少专项材料不能算通过，也不应变成无关普通代码回归的前提。

只有双方有效成果保留、合并引入的回归和交互问题已修复、受影响业务流程有组合可用性证据、稳定候选完成适用的最终验证，且没有会改变结论的未决事项，才能称实际合并任务完成。merge commit 已生成、解冲成功、定向测试通过和未验证清单都只是阶段进度。

缺环境或材料时，先在授权范围内主动准备隔离环境、排查和修复；不能因本机平台不同或已经提交就收尾。只有核实具体私有材料、访问限制或授权缺口后，才报告阻塞、影响与解除条件；继续独立工作，并保留任务未完成状态。历史兼容、迁移和外部验证义务按真实支持范围核实，不为未上线能力虚构包袱，也不以未取得现场证据断言没有义务。

源或目标继续变化时，只追加受新差异影响的分析和验证。交付报告区分源码已整合、合并任务完成与已部署，给出各自证据及尚未闭合事项；完成标准不扩大推送、发布、部署或真实外部操作授权。

需要选择历史查询或文字合并预检工具，或理解调研补充时，读取[方法依据与工具边界](references/methodology-and-tools.md)。
