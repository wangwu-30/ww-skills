# 沉淀工程经验

改进下一次决策，而非增加文档数量。使用仓库既有知识位置和当前授权；不要为此流程创建项目专用包装层。

## 选择受影响的知识

阅读任务与实际 diff、相关指令和架构入口、Owner 的纠正、失败方案及可用执行证据。只读相关知识，默认不通读整个仓库。既有索引用于导航；直接浏览目录或搜索更合适时就直接使用。不要在推进任务前修补完整索引或给全部历史 Lesson 分类。

可复用的经验必须有可观察的触发条件，并能改变当前局部实现之外的未来决策。试着去掉名称、版本和路径：剩下的规则仍有帮助吗？若没有，就把事实留在原规范、Decision、Runbook 或任务证据中，不要写成通用 Lesson。

必须忠于任务范围。相邻缺陷、不完整抽象或更全面的设计，都不等于获准扩大任务。区分必需工作、可选加固和未来能力。未经适用的决策，不改变业务归属、公开合同、执行权限或数据生命周期。

## 先诊断，再添加规则

对每项重要纠正，找出错误及当前流程漏检的原因：

- Agent 不知道真实目标、环境或 Runtime 身份：改进既有工具可观察到的上下文。
- 测试绕过正式入口或真实消费者：在真实边界修回归。
- 知识错误、重复、隐蔽或范围过宽：更新其既有来源和任务入口。
- 机制没有独立价值或真实消费者：考虑删除，包括专用测试和调用方。
- 反复出现且不直观的决策需要步骤：先改进既有 Skill，再考虑新增。

不要认为每次失败都需要 checker、每条经验都需要 Skill，或每项合格纠正都需要新文件。普通措辞、标题、字数与导航选择交给 Review。保留真实授权、兼容、身份、事务和副作用保护。

## 选择最小且持久的改动

动笔前先找相同的未来决策或行为类别。有效结果可以是**复用**、**更新**、**合并**、**建议退出**、**新 Lesson**，或**不新增知识**。既有模板有帮助时使用；没有事实就省略空仪式。

有用的决策记录应保留原假设、改变判断的证据、实际考虑过的替代方案、选择及适用范围。说明被否决方案在什么条件下值得重议。不要为填满模板而虚构选项，也不要把旧 Accepted Decision 静默改写成相反结论。

承重机制可以是既有类型、消费者检查、focused 回归测试、脚本、Review 判断或明确负责的 Owner。只有在能拦住真实错误或节省重复劳动时才自动化；不能仅因要求重要或技术上可检查就新增 validator。

删除文档 checker 时，同时删除死 import、调用和仅支持它的测试；不要保留只会成功的 shell，或换一套新的合规框架。删除生产机制前，必须先识别真实消费者、动态或配置用途，以及需要支持的兼容义务。

## 仅在需要时考虑 Skill

候选 Skill 必须在故障发生前识别情境，改变下一步动作，写明禁止的捷径和停止边界，并有真实可行的选择、拒绝、停止案例。搜索索引、摘要、单个本地字段规则或一次事故都不够。复用既有归属，不创建转发包装层。

值得新建或加强 Skill 时，按仓库 MR 说明要求写清触发情境、改变的行为、与已有 Skill 的分工和验证方式，由 Owner 在 MR 中决定是否采用。证据还不够时，写明缺什么、下次在什么情况下重新考虑。不另建台账、回执格式、试行阶段或反馈账本。

若实施候选超出已分配范围，说明限制并取得必要决策。不要隐式安装、发布、启用 Skill 或扩大工具权限。

## 对照实际改动收尾

使用既有 MR/任务身份、diff、CI 运行、日志和制品。报告改了什么、实际检查了什么、未运行什么以及仍有哪些不确定性。读过此文件、Skill 目录有效或写下 PASS，都不能证明流程或产品通过。

候选、目标或依赖改变时，重新检查新 diff 并更新受影响结论；发布证据仍须满足仓库的精确候选 Gate。不要为普通文字审查新增逐文档 hash 或独立上下文/回执子系统。

先修好范围内的实现，再宣称收尾。相关含义变化时更新 MAP 链接或 Decision；不改写无关知识。不新增知识是正常结果，可以简短说明。

## 退出与后续使用

判断未来决策价值，不以年代、篇幅或删除配额为依据。已修复事故仍可能留下有用约束或被否决的方案。提出具体合并/退出路径；删除历史 Lesson 或退出已启用 Skill 时，遵循仓库既有批准政策。本流程不是概括性的删除授权。

下一个相似任务应通过既有 MAP 入口或 Skill 触发器遇到修正后的来源。在这种任务真实发生前，只报告“已实施改动，效果未验证”，不能声称自我进化已证实。后续观察到反复失败、误触发或不必要成本时，应修订或撤回改动。
