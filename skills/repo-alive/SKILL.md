# repo-alive — 压缩着理解代码仓库

## 0. 这个 skill 是什么

一条北极星:教 agent **压缩着理解**一个代码仓库。agent 上下文有限,仓库无限大,所以不能全量展开——必须从业务目标出发,逐层压缩展开,把仓库压成一套分层、可复用、可下钻的知识,再据此回答问题。

代码是对业务的抽象和实现。所以理解的入口是**业务**,不是代码结构本身。仓库名/服务名往往就压缩了核心业务目标(`ad_predict` = 预估,产出是分)。

**这个 skill 是拐杖。** 现在模型还不会自觉压缩,需要这套指导;以后模型自己会压了,整套都可扔。所以下面分道、法、术三层:道法是北极星,术可换。

---

## 一、道(永不过时)

### 压缩是理解的根本约束

模型上下文不可能无限大(再大也是有限),所以**必须压缩着理解**,不能全量展开。这条永远成立。

变的只是"谁来压缩":现在是 skill 教模型怎么压;以后模型可能自己学会压缩(神经网络本身是压缩的产物)。道不变,法的承载者会迁移。

### 代码是对业务的抽象和实现

理解代码的入口是业务目标,不是代码结构。代码结构是手段不是目的。

---

## 二、法(教当下模型怎么压缩,偶尔变)

### 1. 从业务目标出发,逐层压缩展开

先定"这服务干什么"(如预估=产出分),再展开主线(获取特征→模型调用→计算分),再深入细节,再深才到具体代码。

**从一棵业务主线树展开,终将汇成一个完全图。** 直接铺全图 = 一次理解全部业务——同一件事,收敛与发散,殊途同归。没有矛盾。

每一层是对下一层的压缩,上一层**不预消化**下一层的细节(否则冗余)。父=概览,子=细节,各司其职。

### 2. infra 与业务分离

代码里为效率做了大量封装(工具类、rpc 框架、日志、监控),这些是不同层级的 infra,支撑业务但不是业务主线。理解时**分开看**,否则被框架代码淹没,抓不住业务主干。

### 3. 确定性优先于推测

能用确定性手段(ls/grep/构建系统)拿到的结构(目录、文件归属、import 关系),**不用 LLM 猜**。LLM 只补"语义"(模块是干嘛的、调用链含义、架构骨架)。

哲学:让 LLM 推理,不让 LLM 发现结构。把失败模式从"结构误解"转移到"正确结构上的推理错误"。

### 4. DDD 视角:划领域、列 command

代码是对业务的抽象,用 DDD 思路映射回去:划分领域(bounded context)、列出 command(业务动作)。把代码结构映射回业务领域,理解才落到业务上。

### 5. 动态配置影响关键分支

复杂业务普遍有动态配置(开关/参数),它们会**在运行时切关键分支**(走哪条链路、启用哪个模型、是否走新泳道)。理解仓库时必须标出这些配置点——否则看代码看到的是"所有分支都存在",但实际运行时哪些生效由配置决定,理解就缺了一角。

这是**法**(思路跨环境不变:动态配置影响分支)。具体配置系统名(TCC/Libra/abtest 之类)是**术**,换个环境就是别的名字,只作例子。

## 三、压缩后的知识:存成什么

存储设计从"选什么作主键"开始——主键选错,后续怎么治都治标。下面按设计顺序:先定主键,再定形态,再定约束。

### 1. 主键:全限定名,不写行号(存储设计的起点)

每个代码实体用**最稳定可 grep 的唯一限定符**作主键——不常变、可 grep、唯一定位(C++ 里依赖/namespace/类/方法,遇重载/特化多义时带签名;别语言如 包.类.方法)。外部库符号用"依赖+类名"等不常变限定符标(如 `[依赖 ad/model_manager_i18n] model_manager::ModelManager`)。

**不写行号**。行号只在单线程改代码(定位光标去改)时有用,纯读分析价值不大;且行号易碎(改一行全漂)、陈旧即误导,更是臆造温床(实测多次臆造都栽在行号上)。要现场佐证就写**文件路径**(稳定),不写行号。

> **可迁移的判断法**:当一个风险类别反复治不住,先问"这个类别能不能整个消除",而不是"怎么更好地查它"。不写行号 = 消灭"行号臆造"整个类别,比"穷举回查行号"(写了再查)治本一个层级。选主键时优先选"根本不产生风险"的载体,而非"产生后再查"的载体。

### 2. 形态:分层摘要 + 渐进式披露(法,原则)

每一层是对下一层的摘要,顶层是整个仓库的全局摘要,向下逐层细化,叶子是具体内容。上一层不预消化下一层的细节(否则冗余)。

读者(或下游 agent)先读顶层摘要知道全貌,需要哪块再往下翻一层,逐层深入——不全量塞进 context。这就是渐进式披露。

**顶层摘要默认四维**(可按仓特点加减):
- **业务架构**:这仓干什么、主线环节、bounded context
- **技术架构**:infra 框架、分层、依赖
- **对外接口(DDD command)**:RPC/MQ/Cron 入口 = 业务命令,不是路径列表
- **动态配置**:影响关键分支的配置开关点(法二.5)

**按业务划分层级,不按目录深度**。目录只是物理容器,业务抽象深度才是理解载体。一个业务环节可能跨多个目录,正常。

**默认深度 3,可按需跳转**。3 是锚点(软建议),简单仓 2 层够、复杂仓 4-5 层都行。agent 按业务复杂度自定,不硬截断。

> **辅助示例**(可换,不是规范):像论文的多级目录,或地图集的分层(国家总图→分省→分城→街道),要哪块翻/放大哪块。比喻只为帮理解"分层+按需下钻",不暗示线性阅读或严格树——本 skill 的内容是 wiki 式唯一+多引用(DAG),见下。

### 3. 形态:wiki 式内容唯一(法,原则)

每个实体(符号/关系/域)在**一处定义**,内容不重复出现;但可被多处**引用**(像 wiki)。A 模块和 B 模块都引用 C,C 的内容只在 C 自己那里,不在 A、B 里复制。

- 导航用的分层摘要是"阅读入口",底层内容是 wiki 式唯一+多引用
- 这是 DAG/图,不是严格树(树里一个节点只能一个父);横向调用关系是另一组边,和层级导航共存

### 4. 带置信度(法,约束)

跨文件/跨服务关系必然有错,每条抽取关系标置信度,低置信标"待验证"。脏数据进 context = 幻觉。

### 5. 预铺止于"能回答全局问题"(法,约束)

预铺只做"地基"(结构/符号/关系稳定子集 + 高层摘要 + 路由表),具体代码块的语义解释**永远按需**,查询时生成、不落盘。否则陷入"摘要的摘要"无限递归,且陈旧摘要误导。叶子永远按需。

### 6. 增量靠文件 hash(术,可换)

文件变了,沿目录/社区树向上传播 stale 标记,只重算受影响的。具体 hash 算法(XXH3 之类)是术,可换。

## 四、固定契约(脚本依赖,必须遵守)

只有**跨脚本-AI 边界**的字段是固定契约,其余 AI 产出的内容给 demo 示例即可、不锁死。

### 必须固定

- **`.repo-alive/fingerprint.json`** 路径 + 其内 **`git_head`** 字段。
  preamble 脚本靠它判 freshness:`fingerprint.git_head == 当前 HEAD` 则已分析、跳过重分析。
  最低契约:`{ "git_head": "<commit-sha>" }`,其余字段 AI 自由加。

就这一个。其余 manifest/graph/nodes 的路径与 schema **全是 demo**(见下),AI 可按"三"的原则自由选择更好的存法。

## 五、demo 示例(术,可换)

以下都是**当前实现示例**,不是规范。模型应按"二、三"的法与原则执行,这些示例只是展示一种可行落地。

### demo 存储布局

**文件名是建议非规范**——按仓特点自由命名。注意:某些 harness 会把 `summary.md`/`report.md` 当"报告文件"拦截写入,遇此改用 `overview.md`/`index.md` 等名字落盘即可,内容形态不变。

```
.repo-alive/
  fingerprint.json        # 契约: {git_head, ...}
  overview.md (或 summary.md)  # 顶层四维摘要(业务架构/技术架构/对外接口命令/动态配置)
  domains/                # 业务域分层摘要(每域一个 md,按业务划分非目录)
  symbols/  (可选)        # 符号(每模块一个 md,全限定名作主键,列函数/类/签名);符号也可并入 domains/,按 wiki 唯一原则别重复
  relations.md            # 关系:调用/导入边,wiki式引用,每条带 [conf: 0.8]
  routes.md               # 入口点(DDD command)+ 关键词倒排
```

边用全限定名 + 文档内链接编码,**不带行号**,例:
```markdown
- `ad_predict::Estimator::estimate_with_model_conf` [定义于 frame/estimator.cpp]
  - [调用] `model_manager::ModelManager::run` [conf: 0.92] [定义于外部lib ad/model_manager_i18n]
```
agent 用 grep 做边遍历(全限定名是代码里真实字符串,可 grep),不需要图数据库,也不需要行号。

### demo 分析流程(展示"从业务目标逐层展开 + 分治"怎么落地)

1. **定业务目标**:看仓库名/README/入口,一句话说出"这服务干什么"(ad_predict=预估产出分)。这是第一层压缩。
2. **展开主线**:从业务目标推出主链(获取特征→模型调用→计算分)。这是第二层。
3. **逐层深入**:对主线每一环,问"它怎么实现"→展开子模块。infra(框架/工具)单独标注,不混进主线。按业务划分层级,不按目录深度。默认深度 3,可按需跳转。
4. **确定性优先**:目录/文件/import/全限定名用 ls/grep 拿,不猜;只在需要"这模块干嘛"时才让 LLM 读文件说语义。
5. **存知识**:按 demo 布局落盘,顶层四维摘要(业务架构/技术架构/对外接口命令/动态配置),全限定名作主键,关系带置信度,wiki 式内容唯一,叶子按需。
6. **收口**:够回答"仓库干嘛+功能在哪"就停,不全量铺到叶子。

### demo 分治与循环(术,锚定不自觉的模型)

分析是**分治**:自顶向下分发子任务 + 自底向上汇总结果(最优至少各一趟)。

但模型不自觉,会跑一趟自顶向下就停、或不回头汇总。给个**可进循环的术**锚定它:

- **自顶向下分发**:把当前层的每个子模块,作为子任务派下去(派给子 agent,或自己分批处理)。子任务只管自己那棵子树的摘要+children。
- **分治边界:允许重叠,确保覆盖,不追求硬切**。子任务范围可以重叠(两个 agent 都碰某模块正常),**漏掉比重复更危险**——漏了理解就缺一角,重复了顶多冗余。wiki 唯一(三.3)让重叠成本低:内容只在一处定义,重复的只是全限定名引用,不复制内容。别为了"干净"按目录硬切,宁可重叠也别漏。
- **自底向上汇总**:子任务返回后,父层把子结果汇总成自己的摘要。汇总时若发现**摘要与某子节点矛盾 / 子结果不清晰** → 打回该子任务重分析(这就是"反复",是分治的执行副产品,不是必须发生的步骤)。
- **循环锚点**:汇总遇矛盾就回到子任务,不硬过。但也要防无限循环——同一子任务重分析超 2 次仍不清,标 `[待核]` 上报,不强求。

> 这是术(可换),不是法。法只说"分治:自顶向下+自底向上"。循环是给不自觉模型的拐杖,模型够强自觉往返就不需要这套骨架。

### demo 产出纪律(防卡死 + 防残缺)

实测暴露:单 agent"想一个写一个、写完再想下一个"会卡死(串行 Write 太慢被判无进展),且容易只铺到前几个文件就停。以下纪律治这两个病根,**是术,但落盘阶段必须守**:

1. **想与写分离**。先把各产出文件的内容成形(在"想"里规划好每个文件写什么、骨架),**再连续批量落盘**。不要"想一个文件 → Write → 再想下一个"。写盘是纯 I/O,应一次跑完,不该穿插思考。
2. **完整性自检(落盘前对照打勾)**。每个产出文件必须给一个状态,不允许"默认跳过":
   - ✅已铺 — 已落盘
   - ⏭️跳过(带原因)— 例:"无独立 HTTP/Cron 入口,routes 并入 summary";"关系极少,并入 symbols 的关键边"。原因要具体,不能写"暂略"。
   跳过的要确保信息没丢(并进了别的文件)。
3. **每文件原子**。单次 Write 写一个完整文件,不中途停笔、不先写半截再补。
4. **大文件不读全量**。落盘阶段若要补某大文件语义,只读相关符号段(用 grep 定位全限定名/符号,读其附近),不整文件读进 context——否则既慢又占预算,正是卡死诱因。注意:grep 定位可临时用行号定位光标,但**行号不写进产出**(见三.1)。

> 若执行环境有 workflow 沙箱(可 return 中间产物让调用方批量落盘),优先用它——"workflow 想、调用方写"是更稳的形态。纯 agent 执行则守上述 1-4。

### demo chat 范式(展示"按需深入"怎么落地)

分析后进入对话。每次回答:
1. 从已存知识找相关节点/域(先读顶层摘要,再按需下钻)
2. 不足则按需读真实文件(key files 优先,大文件跳过)
3. 答 + 全限定名引证(符号用 `namespace::Class::method`,定义在哪个文件)
4. 不臆造,不确定就明说并继续读

- "X 怎么工作?" → 找节点 → 读文件 → 追调用链
- "X 和 Y 区别?" → 都加载 → 带证据对比
- "走一遍场景" → 读摘要 → 沿主线展开步骤

铁律:**只从真实文件答。每个事实带全限定名引证。不臆造。不写行号(行号纯读分析价值不大,且易臆造)。**

> 不写行号 = 直接消灭"行号臆造"类别(实测多次臆造都栽在行号上:张冠李戴、偏移)。主键用全限定名(稳定可 grep)。要现场佐证就写文件路径。

### 铁律.2 死代码 / 0-caller 断言验证(防误判事故)

任何"0 caller / 仅 test / 废弃 / 死代码"类断言,**必须 grep 完整生产链确认无 caller 才能下**。生产链至少含:`main/server.cpp` / 各 `init_instance` / 各 collector 的 `run`/`ack_run` / 各 strategy 的 `do_*` / PSM 入口。没查全就标 `[caller 待核,疑似死代码]`,**不能下确定结论**。

特别注意签名变体:grep 精确签名(如 `AckController::run`)查不全——要追 `nearline_run`/`hybrid_run`/`init_instance` 等变体。实测反例:断言"i18n/frame AckController 生产 0 caller 仅 test",实际是活链路 `server.cpp init_instance → i18n_info_collector.cpp ack_run → controller.cpp` 三变体都有 caller。这类误判若进删代码/降级决策 = 线上事故。

> 外部库符号(本仓无定义,如 `model_manager::ModelManager::run` 定义在依赖里)标 `[定义于外部lib <依赖名>,本仓无header]`,不裸写本仓文件假装定义在这——否则 grep 本仓找不到定义易误判死代码。

## 0.5 Preamble(脚本契约,固定)

```bash
REPO_ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
GIT_HEAD=$(git rev-parse HEAD 2>/dev/null || echo "NO_GIT")
DATA_DIR="$REPO_ROOT/.repo-alive"
FINGERPRINT="$DATA_DIR/fingerprint.json"

FORCE_ANALYZE="no"
for arg in "$@"; do
  case "$arg" in
    analyze) FORCE_ANALYZE="yes" ;;
  esac
done

FRESH="no"
if [ "$FORCE_ANALYZE" = "yes" ]; then
  echo "MANIFESTS_FRESH: no (forced)"
elif [ -f "$FINGERPRINT" ]; then
  STORED=$(python3 -c "import json; d=json.load(open('$FINGERPRINT')); print(d.get('git_head',''))" 2>/dev/null || echo "")
  [ "$STORED" = "$GIT_HEAD" ] && FRESH="yes"
fi
echo "MANIFESTS_FRESH: $FRESH"
```

`MANIFESTS_FRESH=no` → 跑分析(按"二、三"的法与原则 + "五"的 demo 示例)。
`MANIFESTS_FRESH=yes` → 直接进 chat。

## 收尾原则

分析完成的判定:能回答"这仓库是干嘛的"+"某功能大概在哪"+ chat 已就绪。不为"覆盖完整"而铺到叶子——叶子永远按需。

**完成度底线(比"能答全局问题"更客观的判定,至少达到):**
- **业务侧**:理清对外暴露的**所有命令**(RPC / MQ / Cron 等)的**全链路**(从入口到完成),以及链路上经过的**领域和实体**。不是只列入口点,是每个命令的完整链路 + 链路上的域/实体。
- **技术侧**:理清**核心依赖**——RPC 框架是什么、MQ 用没用(哪个)、存储用什么、业务框架有没有(是什么)。

这两条是底线,达不到不算分析完。达到了再按"叶子按需"收口,不无限铺。
